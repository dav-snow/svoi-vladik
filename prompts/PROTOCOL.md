# Протокол контроля ИИ-исполнителя

Роли:

- **Владелец** — Костя. Отдаёт ТЗ исполнителю, принимает решения, отзывает секреты, пушит.
- **Надзиратель** — ИИ-агент (я). Пишет ТЗ, проверяет диффы, запускает сборку и проверки, выносит вердикт. Код в проект не пишет без отдельной просьбы.
- **Исполнитель** — внешний кодинг-агент с большим лимитом токенов. Пишет код строго по ТЗ.

## Цикл работы (одна итерация)

1. Надзиратель пишет ТЗ в `prompts/task-NNN-*.md`.
2. Владелец отдаёт ТЗ исполнителю **дословно**, целиком, без сокращений.
3. Исполнитель работает в отдельной ветке `agent/NNN-<тема>`, коммитит и **не пушит в `main`**.
4. Исполнитель отчитывается по шаблону отчёта (ниже).
5. Надзиратель читает `git diff`, запускает проверки из ТЗ, сверяет с контрактом.
6. Вердикт: **ACCEPT** либо **REWORK** с нумерованными пунктами.
7. При REWORK надзиратель пишет `prompts/task-NNN-fix.md` — только исправления, без расширения объёма.

Одна задача = одна ветка = один активный исполнитель. Два агента в одном checkout не работают.

## Жёсткие правила для исполнителя

- Не коммитить в `main`, не делать `force push`, `reset --hard`, `git clean -xfd`.
- Не менять файлы вне списка «разрешённые пути» из ТЗ.
- Не добавлять зависимости без явного разрешения в ТЗ.
- Не придумывать контент: тексты мест, факты, цены, часы — только из `data/` или от У3.
- Не менять контракт (`docs/API.md`) самостоятельно; расхождение — вопрос в отчёте.
- Не трогать `.env`, секреты, `.github/`, `data/geo/`.
- Не удалять и не «упрощать» существующие проверки, обработчики ошибок и fallback.
- Все команды проверки из ТЗ должны реально выполняться; вывод — в отчёт.
- Если ТЗ противоречит коду или докам — стоп и вопрос в отчёте, а не «как понял».

## Шаблон отчёта исполнителя

```
Ветка и коммиты:
Что сделано (по пунктам ТЗ):
Файлы изменены:
Как проверял (точные команды и результат):
Отклонения от ТЗ / вопросы:
Что НЕ сделано и почему:
```

Отчёт без реально выполненных команд не принимается.

## Формат вердикта надзирателя

Метки по убыванию важности: `[БЛОКЕР]`, `[БАГ]`, `[РИСК]`, `[СТИЛЬ]`, `[ВОПРОС]`.
Каждый пункт: метка → файл:строка → в чём проблема → как воспроизвести → что требуется.

ACCEPT ставится только если: сборка проходит, проверки из ТЗ выполнены, контракт не сломан, секретов нет, дифф не содержит лишних файлов.

## Что надзиратель проверяет сам, не доверяя отчёту

- `git diff main...agent/NNN-*` целиком, включая посторонние файлы.
- `docker build` + запуск контейнера + реальные запросы к ручкам.
- `GET /openapi.json` — список путей и коды ответов.
- Соответствие `docs/API.md` и `INTEGRATION.md`.
- Отсутствие секретов: греп по диффу, проверка `.git/config` на токены в URL.
- Наличие и осмысленность тестов: тест, который ничего не проверяет, — `[БАГ]`.
