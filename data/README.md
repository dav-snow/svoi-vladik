# Каталог данных

Здесь будут храниться подготовленные вручную данные MVP. На подготовительном этапе реальных карточек ещё нет: целевой объём 15 мест, до 3 актуальных бесплатных событий и один квест на 3 точки — это план сбора, а не уже проверенный каталог.

Перед добавлением записи прочитайте [правила проверки и список первичных источников](../docs/DATA_POLICY.md). API-контракт и окончательную структуру JSON команда согласует в [docs/API.md](../docs/API.md).

Сбором и редакторской проверкой занимается участник 3 — продакт-менеджер и редактор городского контента. Он передаёт таблицу мест и событий, тексты памяток и квеста с источниками. Бэкендер (участник 2) импортирует материалы в JSON и проверяет структуру; участник 1 совмещает дизайн и фронтенд и проверяет отображение. Писать JSON участнику 3 не обязательно. Состав таблиц и порядок передачи описаны в [ROLE_3.md](../docs/ROLE_3.md).

Предлагаемые наборы после согласования схемы:

- `places.json` — карточки мест для учёбы, творчества, встреч и отдыха.
- `events.json` — проверенные события с датами, часовым поясом, ценой и условиями; пустой массив допустим.
- `tips.json` — памятки новичку и внешние транспортные ссылки.
- `quests.json` — сценарий квеста с привязкой к местам и проверенным историческим фактам.

Каждой записи нужны стабильный `id`, конкретный `source_url`, `checked_at`, `status` и срок перепроверки. Черновики не попадают в пользовательскую выдачу. Не добавляйте настоящие названия мест с выдуманными адресами, ценами или часами работы ради заполнения макета.

Для разработки допустимы отдельные синтетические фикстуры с очевидной маркировкой `demo`, без смешивания с проверенными данными. Они нужны для загрузки, пустых состояний и ошибок; на демо их следует называть тестовыми данными.

Карточка готова к публикации, когда человек сверил существенные поля по первоисточнику, записал дату проверки, проверил условия использования текста/медиа и перевёл её в `verified`. Для исторических фактов квеста нужна повторная проверка другим участником команды.
