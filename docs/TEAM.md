# Команда и порядок работы

Проект: **«Свой Владик»** — помощник, который помогает освоиться во Владивостоке, найти подходящее молодёжное пространство и познакомиться с историей города через короткий квест.

Это план подготовки и будущей разработки. По распределению команды первый участник совмещает дизайн и фронтенд, второй делает бэкенд. **Третий — продакт-менеджер и редактор городского контента:** отвечает за пользовательскую задачу, проверенные данные, квест, приёмку и подготовку защиты. Программирование для этой роли не обязательно. Имена участников и фактический срок вайбатона пока не заданы; у каждой задачи должен быть один ответственный.

## Роли и конкретный результат

| Участник | Зона ответственности | Что передаёт команде | Как принимаем результат |
|---|---|---|---|
| Участник 1 — дизайнер и фронтендер | UX/UI, React + TypeScript + Vite, адаптивные экраны, карта и список, подключение API, сборка | Короткий прототип основного пути и набор компонентов; работающий интерфейс; локальный прогресс квеста; сборка и инструкции запуска клиента | Основной путь проходит на телефоне и ноутбуке; карта и список показывают те же места; ошибки и пустые состояния обработаны; сборка проходит |
| Участник 2 — бэкендер | Контракт API, хранение каталога, фильтрация, подбор; при готовом MVP — работа с моделью | FastAPI-сервис; согласованный контракт; загрузка проверенных данных; пример конфигурации; обработка ошибок; инструкции запуска | Фронтенд получает данные по согласованной схеме; неизвестные идентификаторы и неверный ввод обрабатываются; подбор работает по фильтрам; при добавлении ИИ его отказ не блокирует приложение, а ключи остаются на сервере |
| Участник 3 — продакт-менеджер и редактор контента | Потребность новичка, границы MVP, источники, городской каталог, сюжет квеста, ручная приёмка и защита | Результаты коротких интервью; таблица 15 мест и до 3 событий; 3–5 памяток; квест на 3 точки с ответами и источниками; баг-репорты; презентация и сценарий демо | Каждая карточка пригодна для импорта и проверена; факт отделён от вымысла; найденные ошибки воспроизводятся по шагам; рассказ о проекте укладывается в 3 минуты |

Технологии — стартовое предложение. До начала реализации команда подтверждает их вместе. Не меняйте стек в середине вайбатона без конкретной причины и оценки времени.

У первого участника совмещены две технические задачи, поэтому прототип ограничиваем основным сценарием и повторно используем компоненты. Третий снимает с него сбор данных, написание квеста, организацию тестирования и подготовку выступления. Подробное задание третьему участнику — [ROLE_3.md](ROLE_3.md).

## Как распределить смежные задачи

- **Городские данные:** третий участник собирает и редактирует, бэкендер проверяет структуру и импортирует. Один из разработчиков повторно сверяет существенные сведения по правилам [DATA_POLICY.md](DATA_POLICY.md). Если сведения не подтверждены, запись не попадает в публичную подборку.
- **Исторический квест:** третий участник отвечает за сюжет, источники, вопросы, варианты и объяснения ответов; бэкендер — за структуру заданий и проверку ответов; первый участник — за прохождение и прогресс. Достоверный факт и вымышленная реплика персонажа помечаются отдельно.
- **ИИ:** команда применяет его при подготовке и разработке и фиксирует работу в [AI_USAGE.md](AI_USAGE.md). Третий участник собирает записи для защиты, каждый автор проверяет свой результат. Интеграция модели в продукт — P1 после рабочего MVP: бэкендер отвечает за модель, третий участник проверяет объяснения на соответствие каталогу, первый — за отображение результата и ошибок.
- **Транспорт и городские особенности:** третий участник готовит 3–5 кратких проверенных памяток, первый добавляет переход во внешний навигатор. Собственный расчёт транспортных маршрутов в MVP не входит.
- **Проверка и защита:** третий участник готовит чек-лист, проводит ручную приёмку, фиксирует ошибки и готовит презентацию и трёхминутное демо. Разработчики исправляют дефекты своих частей, проверяют запуск и размещают демо. Третий ведёт рассказ, первый показывает интерфейс; каждый отвечает за свою область.

## Сначала договориться о стыках

В первые часы третий участник формулирует основной сценарий и критерии приёмки, вся команда подтверждает объём. Бэкендер и первый участник согласуют [API-контракт](API.md): поля карточки места, события, квеста и подборки, форматы ошибок и примеры ответов. Первый начинает интерфейс на этих примерах, пока API готовится. Третий сразу заполняет каталог в согласованной таблице, а не передаёт разработчикам разрозненные ссылки. Правила проверки сведений описаны в [DATA_POLICY.md](DATA_POLICY.md).

Ориентир для полей места: стабильный `id`, название, координаты, адрес, категория, интересы, стоимость или отметка «уточнить», условия посещения, источник, `checked_at`. Неизвестная стоимость не считается бесплатной. У события дополнительно нужны время, часовой пояс `Asia/Vladivostok`, регистрация и ссылка на организатора. Не используйте тексты названий как идентификаторы.

Карта не должна блокировать весь продукт: те же места доступны списком. Геолокация необязательна — пользователь может выбрать старт вручную. В MVP не требуются аккаунты: избранное и прогресс можно хранить локально в браузере. Не сохраняйте историю перемещений.

## GitHub и совместная работа

1. Ведите задачи из [BACKLOG.md](BACKLOG.md) в GitHub Issues. В каждой задаче — один владелец, результат, критерий готовности и зависимости. Статусы: `Todo → In progress → Review → Done`. У участника одновременно не более одной основной задачи.
2. `main` хранит согласованное состояние. Для задачи создавайте короткую ветку: `feat/places-list`, `feat/places-api`, `docs/quest-sources`, `fix/empty-state`. Не используйте общую ветку для параллельной работы.
3. Делайте небольшие осмысленные коммиты. В pull request укажите, что изменилось, ссылку на задачу, как проверили; для интерфейса приложите скриншот. Черновик PR можно открыть рано, чтобы показать стык.
4. Один другой участник проверяет PR. Разработчики взаимно смотрят API и интеграцию; третий проверяет содержание, сценарий и критерии приёмки. Техническое ревью остаётся у разработчиков. Автор исправляет замечания; после проверки PR объединяется в `main`.
5. Перед объединением заберите свежий `main`, разрешите конфликты в своей ветке и повторите затронутый сценарий. Изменение API в том же PR сопровождайте обновлением контракта и примера ответа.
6. Общайтесь короткими синхронизациями на старте, после первого сквозного сценария и перед релизом. При активной работе каждые 2–3 часа сообщайте: «сделано / следующий результат / блокер». О блокере сообщайте сразу, а не в конце дня. Третий участник обновляет статусы и помогает сократить объём, если задача не укладывается; новые функции команда согласует вместе.

Для работы втроём понадобятся GitHub-логины участников. Доступ к репозиторию выдаёт владелец; пароли, токены и файлы `.env` в репозиторий не добавляются.

## Как использовать ИИ с пользой

ИИ помогает команде с черновиками текстов, вариантами экранов, кодом, разбором ошибок и ревью. В задаче фиксируйте контекст и критерий результата: «реализуй фильтр по этим полям и проверь такие случаи» полезнее, чем «сделай приложение».

Для P1 в самом продукте достаточно одной понятной функции: запрос «хочу бесплатно поучиться и узнать историю» превращается в подборку из проверенного каталога с кратким объяснением. Модель получает только разрешённые записи, возвращает их идентификаторы, а сервер проверяет их существование. Недоступные или выдуманные места отбрасываются. Цены, расписание, транспортные сведения и исторические факты берутся из базы с источниками, а не из памяти модели.

Если P1 реализован, но модель недоступна или ответ не прошёл проверку, включается обычный подбор по фильтрам. Точное местоположение, личные сведения и секреты не отправляются в модель без необходимости. Ключ модели используется только на сервере. До P1 основной сценарий полностью работает на фильтрах и заранее проверенном квесте.

Ведите короткий журнал использования ИИ: задача, инструмент/модель, что получили, что исправили и как проверили. Это материал для защиты и объяснения собственного вклада. Сгенерированный код обязательно прочитать, запустить и проверить по пользовательскому сценарию.

## Готовность к защите

- Основной путь целиком работает: интересы → подборка → место → внешняя навигация → квест → результат.
- Каталог содержит 15 проверенных мест; события актуальны и подтверждены либо показано честное пустое состояние; квест содержит 3 точки с источниками.
- Есть краткая помощь новичку по транспорту и особенностям города; ссылки проверены перед демонстрацией.
- Есть состояния загрузки, ошибки, отсутствия результатов и отказа в геолокации; подбор работает без подключения модели.
- README позволяет другому участнику запустить проект; конфигурация описана без секретов; публичный репозиторий открывается без входа.
- Подготовлены трёхминутная демонстрация и запасная запись на случай проблем с сетью.
