# Команда и порядок работы

Проект: **«Свой Владик»** — помощник, который помогает освоиться во Владивостоке, найти подходящее молодёжное пространство и познакомиться с историей города через короткий квест.

Это план подготовки и будущей разработки. Имена участников и фактический срок вайбатона пока не заданы. Третью роль предлагаем закрепить за фронтендером, который также отвечает за интеграцию и демонстрацию. Один человек может совмещать обязанности, но у каждой задачи должен быть один ответственный.

## Роли и конкретный результат

| Участник | Зона ответственности | Что передаёт команде | Как принимаем результат |
|---|---|---|---|
| Дизайнер — UX/UI и редактор контента | Пользовательский сценарий, интерфейс, визуальная система, понятность текстов | Кликабельный мобильный прототип; компоненты и состояния; макеты; 15 карточек мест, подборка событий и тексты квеста с источниками | Можно пройти путь от выбора интересов до карточки места и задания квеста; есть загрузка, ошибка, пустой результат и отказ в геолокации; у фактических утверждений указаны источники и дата проверки |
| Бэкендер — API, данные и ИИ | Контракт API, хранение каталога, фильтрация, подбор; при готовом MVP — работа с моделью | FastAPI-сервис; согласованный контракт; загрузка проверенных данных; пример конфигурации; обработка ошибок; инструкции запуска | Фронтенд получает данные по согласованной схеме; неизвестные идентификаторы и неверный ввод обрабатываются; подбор работает по фильтрам; при добавлении ИИ его отказ не блокирует приложение, а ключи остаются на сервере |
| Фронтендер — приложение, интеграция и демо | React + TypeScript + Vite, адаптивные экраны, карта и список, подключение API, сборка | Работающий основной сценарий; состояния интерфейса; локальное сохранение прогресса; избранное — P1; доступный URL или воспроизводимый локальный запуск; сценарий демонстрации | Приложение проходит согласованный сценарий на телефоне и ноутбуке; маркер и карточка относятся к одному месту; переход во внешнюю навигацию работает; сборка проходит; при сетевой ошибке есть понятное действие |

Технологии — стартовое предложение. До начала реализации команда подтверждает их вместе. Не меняйте стек в середине вайбатона без конкретной причины и оценки времени.

## Как распределить смежные задачи

- **Городские данные:** дизайнер собирает и редактирует, бэкендер проверяет структуру и импортирует. Второй участник выборочно сверяет факты с первоисточниками. Если сведения не подтверждены, запись не попадает в публичную подборку.
- **Исторический квест:** дизайнер отвечает за сюжет и источники, бэкендер — за структуру заданий и проверку ответов, фронтендер — за прохождение и прогресс. Достоверный факт и вымышленная реплика персонажа помечаются отдельно.
- **ИИ:** команда применяет его при подготовке и разработке и фиксирует работу в [AI_USAGE.md](AI_USAGE.md). Интеграция модели в продукт — P1 после рабочего MVP: бэкендер отвечает за модель, дизайнер проверяет ясность объяснений, фронтендер показывает загрузку, результат и резервный вариант. Финальную ответственность за сгенерированное несёт человек, который принимает изменение.
- **Транспорт и городские особенности:** дизайнер готовит краткие проверенные памятки, фронтендер добавляет переход в выбранный внешний навигатор. Собственный расчёт транспортных маршрутов в MVP не входит.
- **Проверка и защита:** каждый проверяет свою часть; затем дизайнер проходит сценарий как новичок, бэкендер проверяет данные и ошибки, фронтендер собирает релиз и ведёт демонстрацию. На вопросы каждый отвечает за свою область.

## Сначала договориться о стыках

В первые часы согласуйте один основной сценарий и [API-контракт](API.md). Бэкендер и фронтендер совместно определяют поля карточки места, события, квеста и подборки, форматы ошибок и примеры ответов. Фронтендер начинает с тех же примеров как с мок-данными, пока API готовится. Правила проверки сведений описаны в [DATA_POLICY.md](DATA_POLICY.md).

Ориентир для полей места: стабильный `id`, название, координаты, адрес, категория, интересы, стоимость или отметка «уточнить», условия посещения, источник, `checked_at`. Неизвестная стоимость не считается бесплатной. У события дополнительно нужны время, часовой пояс `Asia/Vladivostok`, регистрация и ссылка на организатора. Не используйте тексты названий как идентификаторы.

Карта не должна блокировать весь продукт: те же места доступны списком. Геолокация необязательна — пользователь может выбрать старт вручную. В MVP не требуются аккаунты: избранное и прогресс можно хранить локально в браузере. Не сохраняйте историю перемещений.

## GitHub и совместная работа

1. Ведите задачи из [BACKLOG.md](BACKLOG.md) в GitHub Issues. В каждой задаче — один владелец, результат, критерий готовности и зависимости. Статусы: `Todo → In progress → Review → Done`. У участника одновременно не более одной основной задачи.
2. `main` хранит согласованное состояние. Для задачи создавайте короткую ветку: `feat/places-list`, `feat/places-api`, `docs/quest-sources`, `fix/empty-state`. Не используйте общую ветку для параллельной работы.
3. Делайте небольшие осмысленные коммиты. В pull request укажите, что изменилось, ссылку на задачу, как проверили; для интерфейса приложите скриншот. Черновик PR можно открыть рано, чтобы показать стык.
4. Один другой участник проверяет PR. Фронтендер смотрит контракт API, бэкендер — его подключение, дизайнер — интерфейс и содержание. Автор исправляет замечания; после проверки PR объединяется в `main`.
5. Перед объединением заберите свежий `main`, разрешите конфликты в своей ветке и повторите затронутый сценарий. Изменение API в том же PR сопровождайте обновлением контракта и примера ответа.
6. Общайтесь короткими синхронизациями на старте, после первого сквозного сценария и перед релизом. При активной работе каждые 2–3 часа сообщайте: «сделано / следующий результат / блокер». О блокере сообщайте сразу, а не в конце дня.

Для работы втроём понадобятся GitHub-логины участников. Доступ к репозиторию выдаёт владелец; пароли, токены и файлы `.env` в репозиторий не добавляются.

## Как использовать ИИ с пользой

ИИ помогает команде с черновиками текстов, вариантами экранов, кодом, разбором ошибок и ревью. В задаче фиксируйте контекст и критерий результата: «реализуй фильтр по этим полям и проверь такие случаи» полезнее, чем «сделай приложение».

Для P1 в самом продукте достаточно одной понятной функции: запрос «хочу бесплатно поучиться и узнать историю» превращается в подборку из проверенного каталога с кратким объяснением. Модель получает только разрешённые записи, возвращает их идентификаторы, а сервер проверяет их существование. Недоступные или выдуманные места отбрасываются. Цены, расписание, транспортные сведения и исторические факты берутся из базы с источниками, а не из памяти модели.

Если P1 реализован, но модель недоступна или ответ не прошёл проверку, включается обычный подбор по фильтрам. Точное местоположение, личные сведения и секреты не отправляются в модель без необходимости. Ключ модели используется только на сервере. До P1 основной сценарий полностью работает на фильтрах и заранее проверенном квесте.

Ведите короткий журнал использования ИИ: задача, инструмент/модель, что получили, что исправили и как проверили. Это материал для защиты и объяснения собственного вклада. Сгенерированный код обязательно прочитать, запустить и проверить по пользовательскому сценарию.

## Готовность к защите

- Основной путь целиком работает: интересы → подборка → место → внешняя навигация → квест → результат.
- Каталог содержит 15 проверенных мест; события актуальны и подтверждены либо показано честное пустое состояние; квест содержит 3 точки с источниками.
- Есть краткая помощь новичку по транспорту и особенностям города; ссылки проверены перед демонстрацией.
- Есть состояния загрузки, ошибки, отсутствия результатов и отказа в геолокации; подбор работает без подключения модели.
- README позволяет другому участнику запустить проект; конфигурация описана без секретов; публичный репозиторий открывается без входа.
- Подготовлены трёхминутная демонстрация и запасная запись на случай проблем с сетью.
