# Команда и результаты по ролям

В команде три человека: **участник 1 совмещает дизайн и фронтенд, участник 2 делает бэкенд, участник 3 ведёт продукт, контент, ручную приёмку и защиту**. План рассчитан на 36 календарных часов с отдыхом; подробная сетка — [IMPLEMENTATION_36H.md](IMPLEMENTATION_36H.md). Имена и логины нужно вписать при старте.

## Участник 1 — дизайн и фронтенд

**Отвечает за работающий пользовательский путь.**

1. Вместе с третьим участником набросать основной путь, затем собрать один мобильный каркас и повторно используемые компоненты. Не тратить первые часы на полировку всех экранов.
2. На согласованных примерах сделать список мест, карточку и фильтры. Подключить реальный API к H6–8.
3. Добавить карту с маркерами, «Я тут впервые», ручной старт и необязательную геолокацию. Радиус считать на клиенте, подписать расстояние по прямой.
4. Собрать просмотр готовых прогулок и переход во внешний навигатор; затем экран точки квеста, ответ, пояснение и локальный прогресс.
5. Добавить самый простой аватар, одну награду и статичного маскота с тремя кнопками. Использовать готовые компоненты и собственные простые значки; сложную анимацию отложить.
6. Проверить мобильную вёрстку, доступность кнопок, ошибки, пустые результаты и сброс локального состояния. С бэкендером проверить размещение и запуск.

**Передаёт:** исходники клиента, сборку, инструкцию запуска, описание публичных переменных окружения и скриншот рабочего пути. **Приёмка:** третий участник проходит сценарий на телефоне; данные совпадают с API, отказ геолокации не блокирует приложение, секретов в сборке нет.

## Участник 2 — бэкенд и техническая интеграция

**Отвечает за контракт, данные API и доступность демо.**

1. За H0–2 зафиксировать с участником 1 [API.md](API.md), примеры ответов и версии зависимостей. Передать третьему шаблон таблицы с устойчивыми ID.
2. Поднять небольшой FastAPI-сервис с JSON-данными, без БД и аккаунтов. Создать health, выдачу мест/прогулок/памяток/квеста и проверку ответов.
3. Начать с первых трёх карточек и синтетических примеров, импортировать итоговый каталог по мере готовности. Отдельно валидировать источники, статусы и ссылки между ID.
4. Реализовать серверную проверку ввода, ограничения запросов, предсказуемые ошибки и безопасное окружение по [SECURITY.md](SECURITY.md). Не доверять проверкам только в UI.
5. Подготовить раннее размещение к H8, HTTPS и адрес API для клиента. Для простоты рассмотреть один origin: собранный клиент и `/api/v1` за одним сервисом. Инфраструктура не должна целиком лежать на перегруженном участнике 1.
6. Взаимно проверить интеграцию с фронтендером, провести серверные проверки и помочь с ошибками. P1 ИИ подключать только после рабочего P0 и с ограничением стоимости.

**Передаёт:** сервис, данные и импорт, примеры конфигурации без секретов, проверенные команды запуска/проверок и адрес стенда. **Приёмка:** клиент получает реальные данные, неизвестные ID и неверный ввод обработаны, ключи не раскрываются, запуск воспроизводится другим участником.

## Участник 3 — продукт, городской контент и приёмка

**Отвечает за полезность, правдивость содержания и готовность к защите. Программировать необязательно.**

1. Прочитать правила вайбатона, провести 3 коротких разговора с целевой аудиторией (до 5 при наличии времени), согласовать одну пользовательскую задачу и приоритеты.
2. Выбрать компактный участок внутри уже утверждённого Ленинского района Владивостока и собрать сначала 3, затем 8 проверенных карточек; 9–10 только в том же районе и при свободном времени. Проверить районную принадлежность объектов, передавать данные частями в согласованной таблице.
3. Подготовить 2 прогулки по 3 точки, 1 квест на 3 точки с правильными ответами и источниками, 3–5 памяток. Проверить проход; не обещать проверенный маршрут, если он не осмотрен.
4. Сверять содержание на реальном экране, вести чек-лист и баг-репорты с воспроизводимыми шагами. Техническое ревью и исправление кода остаются у разработчиков.
5. Следить за контрольными точками и предлагать сокращение объёма; новые функции команда принимает вместе. К H27 закрыть список функций.
6. Подготовить 5–6 слайдов, трёхминутное демо, запасную запись и журнал использования ИИ. Вести рассказ на защите, разработчики показывают интерфейс и отвечают за свои части.

**Передаёт:** таблицу, тексты и источники, список результатов проверок, презентацию и сценарий. **Приёмка:** материалы готовы к импорту без поиска недостающих фактов разработчиками; правила бесплатности и факты квеста повторно сверены другим участником. Подробное задание — [ROLE_3.md](ROLE_3.md).

## Как работаем вместе

Границы файлов и точные команды Git — [PARALLEL_WORK.md](PARALLEL_WORK.md). В основе: каждый работает в своей ветке/локальной копии, API согласуется до параллельной реализации, общие файлы имеют владельца. По одному человеку на один набор файлов; одна нейросеть не редактирует те же файлы одновременно с другой.

Каждые 2–3 активных часа — короткая сверка «готовый результат / следующий результат / блокер». Блокер сообщаем сразу. В PR указываем критерий, проверку и вклад ИИ; другой участник принимает изменение. Разработчики проверяют код друг друга, третий — содержимое и сценарий. API и данные меняются совместно с примерами и контрактом.

Безопасность и достоверность входят в готовность каждой задачи. Статус «готово» означает проверенный результат в общей сборке, а не только ответ нейросети или локальный скриншот.
