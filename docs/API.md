# API v1 — фактический контракт

Документ описывает **реализованный** API текущей демо-сборки. Источник истины для
машинной проверки — `GET /openapi.json`; запуск и интеграционные детали —
[INTEGRATION.md](../INTEGRATION.md). Тест `backend/tests/test_docs_contract.py`
падает, если список путей здесь разойдётся с OpenAPI.

**Это демо.** Каталог содержит кандидатов `draft` с явной пометкой; статус
`verified` никому не присваивается автоматически. Принадлежность району означает
проверенное положение точки, а не подтверждение цены, часов работы или входа.
Есть демо-аккаунты, SQLite, лайки, отметки посещений, профиль и топ. Нет
отзывов, загрузки фото, email/восстановления пароля, 2FA, мультиплеера и
собственной маршрутизации.

**География — только Ленинский район Владивостока.** Радиус и геолокация
считаются на клиенте и в API не передаются.

## Общие правила

- Стабильный ID: 1–64 символа ASCII `[A-Za-z0-9_-]`. Названия ключами не служат.
- Координаты: `{ "lat": number, "lng": number }`; широта −90…90, долгота −180…180,
  только конечные числа. У неактивной записи координаты могут быть `null`.
- Статусы: `draft`, `verified`, `needs_review`, `expired`, `archived`. Публичная
  выдача демо — `draft` и `verified`, только с `active: true` и
  `district_verified: true`.
- Цена: `price_rub: integer | null`. `null` — «неизвестно», а не «бесплатно».
  Неизвестная цена не проходит фильтр бюджета.
- Источники: `source_url` и `sources: [{ "title": "…", "url": "https://…" }]`.
  API их не загружает и не проксирует.
- Ответы — данные, не HTML. Тексты каталога и квестов выводятся как текст.
- Времена — ISO 8601 с часовым поясом; `checked_at: null` допустим и означает,
  что проверка не выполнялась.

возвращает 404, даже если каталог случайно попал в статику. Старый `/api/*`
(без `v1`) не поддерживается.

## Фильтры мест

- `category` — одно значение из `culture`, `viewpoint`, `park`, `food`, `toilet`, `other`.
- `max_price_rub` — целое 0…100000.
- Фильтры применяются совместно. Неизвестное значение, повтор параметра, дробь или
  отрицательное число → 422. Пустой результат — 200 с пустым `items`.

## Place

`id`, `name`, `description`, `category`, `coordinates`, `status`,
`district_verified`, `active`, `price_rub`, `checked_at`, `source_url`,
`sources[]`, `verification_note`; необязательные `address`, `image`, `images[]`,
`osm_tags`. Вычисляемое поле `route_url` — готовая пешеходная ссылка 2ГИС
(`https://2gis.ru/directions/tab/pedestrian/points/|<lng>,<lat>`, с сырым `|`),
её клиент использует как есть.

`images` — галерея места (порядок = порядок показа, первый элемент — обложка):
`[{ "url", "alt", "caption", "source_url" }]`. `url` — путь `/assets/places/...`
(лицензированный пак) или `/media/...` (редакционные фото), либо публичный
`https://`; `alt` для доступности, `caption` и `source_url` необязательны.
Старое одиночное поле `image` сохранено для совместимости. Фото-пак
`assets/places/` подключается скриптом `scripts/link_place_photos.py`; в
`caption` сохраняются автор, лицензия и ссылка на её условия.

Дополнительно каждая карточка несёт четыре вычисляемых социальных поля:
`visits: int`, `likes: int`, `visited_by_me: bool`, `liked_by_me: bool`.
Они считаются из базы на лету и в JSON-файлы каталога не записываются.
Для анонимного запроса оба `*_by_me` всегда `false`. Если база недоступна,
счётчики честно равны нулю, а каталог продолжает работать.

## Демо-авторизация

Вход по логину и паролю — осознанная рамка демо: **нет email, восстановления
пароля, 2FA, ролей и удаления аккаунта**. Не используйте реальные пароли от
других сервисов. Логин виден другим в рейтинге.

- Логин: 3–32 символа `[A-Za-z0-9_.-]`; пароль: 8–128 символов.
- Пароль хранится только как `scrypt`-хэш с солью (`n=16384, r=8, p=1`);
  в открытом виде он не появляется ни в базе, ни в логах, ни в ответах.
- Сессия — серверный токен в куке `sv_session`: HttpOnly, SameSite=Lax,
  Path=/, Max-Age 7 дней. В базе хранится только SHA-256 токена. На HTTPS
  обязательна переменная `COOKIE_SECURE=1`, добавляющая флаг Secure.
- `POST /auth/register` и `POST /auth/login` ограничены: не больше 10 попыток
  в минуту на IP и отдельно на логин; превышение — 429 с `Retry-After: 60`.
- Неверная пара логин/пароль всегда даёт одинаковый 401 без уточнения,
  что именно неверно.

## Посещения, лайки, профиль и рейтинг

Все записи требуют сессии (иначе 401) и известного места (иначе 404).
**Посещение — это отметка пользователя, а не подтверждённый визит**: сервер
не проверяет геопозицию и не доказывает присутствие. Счётчики демонстрационные.

- `POST /places/{id}/visit` и `POST /places/{id}/like` идемпотентны: повтор
  той же отметки не растит счётчик — пара (пользователь, место) уникальна.
- `DELETE` снимает отметку и тоже идемпотентен. POST и DELETE этих ручек
  делят общий лимит 30 запросов в минуту на IP, чтобы цикл
  «поставил/снял» не был бесплатным.
- Посещения и лайки независимы: лайк не означает посещение и наоборот.
- `GET /me/profile` возвращает только собственные данные:
  `{ "user": { "id", "login" }, "stats": { "visits": N, "likes": M },
  "visited_place_ids": [...], "liked_place_ids": [...] }`.
  Чужие полные профили не отдаются.
- `GET /leaderboard?limit=10`: только пользователи хотя бы с одним посещением;
  сортировка строго по `visits` по убыванию, при равенстве — по `login` по
  возрастанию. `likes` показываются, но на место в топе не влияют. `limit`
  1–20 (по умолчанию 10); значение вне диапазона, повтор или лишний параметр —
  422. В ответе только `login`, `visits`, `likes` — без ID, дат регистрации
  и списков мест.

Хранилище — локальный SQLite-файл (`DB_PATH`, по умолчанию
`data/demo.sqlite3`), создаётся автоматически при старте. Если база
недоступна или повреждена, API не падает: счётчики мест равны нулю,
рейтинг пуст, а записывающие ручки отвечают 503.

## Обучение новых пользователей (Влада)

Сценарий и реплики — в [VLADA_AND_ONBOARDING.md](VLADA_AND_ONBOARDING.md); API
хранит только прогресс знакомства для аккаунта. У нового пользователя
`status = "pending"`. Обучение не отмечает посещения и не засчитывает квест.

- `GET /me/onboarding` →
  `{ "status", "step", "interest", "started_at", "updated_at", "completed_at" }`.
- `PUT /me/onboarding` — частичное обновление, не переданные поля не меняются:
  `status` ∈ `pending|in_progress|completed|skipped`, `step` — id шага
  (`[a-z0-9_-]`, 1–64), `interest` ∈ `places|walks|quest`. Недопустимые значения
  или лишние поля → 422.
- `started_at` ставится при первом переходе из `pending`; `completed_at`
  заполняется только при `completed` и сбрасывается при возврате в
  `pending`/`in_progress`.
- `GET /me` включает `onboarding`, чтобы клиент решал, показывать ли знакомство
  (не показывать при `completed`/`skipped`).

## Guide — практический гид

`data/guides.json`: карточки для бытовых нужд — поесть, туалет, досуг, ночлег.
Сейчас это **только адрес, ориентир цены и источник**: координат входа нет, поэтому
такие точки не показываются на карте и по ним не строится маршрут. Так сделано
намеренно: адрес из справочника не равен проверенному входу.

Поля: `id`, `title`, `need` (`eat`, `toilet`, `fun`, `lodging`), `address`,
`price_note`, `note`, `source_url`, `sources[]`, `checked_at`, `status`,
`verification_note`. У всех записей статус `draft`: работа, часы и цена не
подтверждены, поэтому интерфейс подписывает их как кандидатов.

`GET /api/v1/guides?need=toilet` фильтрует по потребности; неизвестное значение или
лишний параметр дают 422. Пустой результат — 200 с пустым `items`. Маскот показывает
карточки текстом, с источником и честной оговоркой, а не как проверенную услугу.

## Walk

`id`, `title`, `description`, `place_ids` (3–5 уникальных ID в порядке прохождения),
`estimated_minutes: integer | null`, `route_note`, `route_checked_at`,
`quest_id: string | null`, общие поля источников и статуса.

`estimated_minutes: null` означает, что длительность не подтверждена; интерфейс не
рисует придуманное время. Линия на карте показывает порядок точек, а не проверенный
пешеходный путь. Маршрут открывается во внешнем навигаторе.

## Quest и QuestStop

`Quest`: `id`, `title`, `description`, `estimated_minutes: integer | null`,
`related_place_ids`, `stop_count`, `stops[]`, `sources[]`, `checked_at`, `status`.

`QuestStop`: `id`, `place_id`, `title`, `fact_text` (подтверждённая справка),
`fiction_text` (явно обозначенный вымысел), `question`, `options: [{ id, text }]`,
`sources[]`, `checked_at`.

Поддерживается 3–5 остановок. `stop_count` равен длине `stops`, ID остановок
уникальны. Правильного ответа и пояснения в публичной выдаче **нет**: модели
перечисляют поля явно, и служебные поля (`correct_option_id`, `explanation`, флаги
правильности вариантов) в GET не попадают.

## Проверка ответа

```http
POST /api/v1/quest/{quest_id}/answer
Content-Type: application/json

{ "stop_id": "stop-id", "option_id": "option-id" }
```

Ответ `200 OK`: `{ "correct": true, "explanation": "…" }`.

| Ситуация | Ответ |
|---|---|
| Известная точка и известный вариант | 200, `correct: true/false` |
| Неизвестный квест, точка или вариант; точка или вариант от другого квеста | 404 `NOT_FOUND` |
| Неверная форма тела, лишние поля, невалидный JSON | 422 `VALIDATION_ERROR` |
| Приватные ключи ответов не готовы | 503 `UNAVAILABLE` |
| Больше 30 POST-проверок за минуту с IP | 429 `RATE_LIMITED`, `Retry-After` |

Повтор ответа разрешён; сервер историю не хранит.

## Завершение квеста

```http
POST /api/v1/quest/{quest_id}/complete
Content-Type: application/json

{ "answers": [ { "stop_id": "stop-id", "option_id": "option-id" } ] }
```

Сервер заново проверяет полноту, уникальность и правильность набора. Пропущенная
точка или известный неверный ответ дают `200` и
`{ "completed": false, "reward": null }`; дубликат `stop_id` — 422; неизвестная
точка или вариант — 404. Полный набор верных ответов возвращает
`{"completed": true}` и **историческое** поле `reward` («Шапка исследователя»),
которое осталось для обратной совместимости. Продукт предметные награды не
показывает, клиент это поле игнорирует; удаление поля — в бэклоге.

Сервер не хранит прогресс квеста за пользователем: последовательность остановок,
ответы и завершение лежат в `localStorage` клиента. Завершение квеста не
подтверждает физическое посещение и не влияет на топ по посещениям.

## Ошибки и ограничения

Любая ошибка: `{ "error": { "code": "SYMBOLIC_CODE", "message": "Понятный текст" } }`,
без трассировки, текста исключения и секретов.

| HTTP | Когда |
|---|---|
| 404 | Неизвестный ID или путь, приватные данные |
| 405 | Неподдерживаемый метод |
| 413 | JSON тела `answer`/`complete` больше 16 КиБ, в том числе поток без `Content-Length` |
| 414 | Query API больше 1024 байт |
| 415 | `answer`/`complete` не `application/json` либо сжатое тело |
| 422 | Невалидный JSON, схема, ID, enum, лишние поля, дубликаты ответов |
| 429 | Больше 30 POST-проверок за минуту на IP |
| 503 | Приватные ключи проверки не готовы |
| 500 | Контролируемая внутренняя ошибка без деталей |

Ключи ответов лежат только в `data/private/quest-answers.json` — это серверная
конфигурация, а не HTTP-ресурс. Схема и порядок подготовки —
[data/private/README.md](../data/private/README.md). Публичный GitHub не защищает
ответы от чтения в исходниках демо, и это осознанно: соревновательной защиты нет.

## Клиентские данные (не API)

Аватары профиля, личный маршрут и прогресс квестов сейчас не передаются в API:
они хранятся в `localStorage` (см. [ARCHITECTURE.md](ARCHITECTURE.md)).
Серверное хранение прогресса и аватаров — задача из [BACKLOG.md](BACKLOG.md);
до неё один и тот же аккаунт на разных устройствах не видит чужой прогресс.
Обучение Влады — исключение: его статус хранится в аккаунте
(`/me/onboarding`), а признак «уже показывали» — на устройстве.

## Вне объёма

Не реализовано и не обещается: серверная синхронизация прогресса квестов и
аватаров, замена точки прогулки, ИИ-подбор, события, отзывы, загрузка фото
пользователями, чат, мультиплеер, email/восстановление пароля, 2FA, удаление
аккаунта, собственная маршрутизация, другие районы и админ-панель. Если
что-то появится, оно сначала описывается здесь и в `/openapi.json`, затем
реализуется вместе с клиентом и тестами.

## Заморозка

Владелец API — бэкенд-разработчик, клиентских типов — фронтенд. Имена и типы
меняются только согласованно: контракт, данные, сервер и клиент обновляются в
одном изменении, старое поведение не ломается молча.
